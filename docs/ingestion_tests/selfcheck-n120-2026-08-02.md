## The decomposition, which matters more than the headline

The model never emits `no_track_fits`. That string is the **human** label vocabulary
(`backend/evals/labels.py:184`, `backend/webapp/label.py:173`). The model's equivalent is
`null` — `backend/extract.py:338` instructs it that *"null is the correct answer for a role
that belongs to no listed track"* — and `backend/evals/tasks/extract.py:29-36` records that
`compare()` scores `None == None` as agreement, which is the reading
`labels.as_model_domain()` depends on. `metrics._flips` stringifies it as `None`.

Reading the raw artifact, the flip patterns spell it `"None"` — that is
`metrics._flips` stringifying Python's `None`, not a value in the vocabulary. The schema says
`null` and the JSON means `null`.

So the question a "group by `role_track`" display actually turns on is: **how often does a
posting move between belonging to a named track and belonging to none?**

| pattern | records | crosses `null`? |
|---|---|---|
| `null` ↔ `business_operations` | 5 | **yes** |
| `null` ↔ `product_and_marketing` | 3 | **yes** |
| `software_engineering` ↔ `solutions_and_implementation` | 3 | no |
| `null` ↔ `revenue_operations` | 2 | **yes** |
| `null` ↔ `solutions_and_implementation` | 2 | **yes** |
| `null` ↔ `data_and_analytics` | 1 | **yes** |
| `business_operations` ↔ `data_and_analytics` ↔ `product_and_marketing` | 1 | no |
| `business_operations` ↔ `revenue_operations` | 1 | no |
| `data_and_analytics` ↔ `software_engineering` | 1 | no |
| `solutions_and_implementation` ↔ `technical_support` | 1 | no |

**13 of 115 records (11.3%, [6.7–18.4]) changed whether the posting belongs to any track at
all** between three runs of the same prompt on the same text. Only 7 of 115 (6.1%) moved
between two *named* tracks.

That ratio is the finding. For `ai_involvement` the boundary crossings were a minority of
the instability; here they are the **majority of it** — nearly two thirds of every
`role_track` disagreement is the model changing its mind about whether the posting is
classifiable, not about which track it belongs to. A grouped display renders that as a
posting entering or leaving the "no track" bucket between one nightly run and the next.

**Majority-of-3 would settle 19 of the 20 unstable records.** Two distinct values over three
runs is a 2–1 majority; three distinct values is not, and one record returned three, so a
third call would not settle it. That is the mitigation [`README.md`](README.md) already names
for `ai_involvement`, reported here so the new field's write-up is commensurable with the
existing one. Nothing here implements it — a measurement task's deliverable is the number.

### This is not the labelling report's 42%, and the two must not be compared

[`../labelling-report-2026-08-02.md`](../labelling-report-2026-08-02.md) reports
`role_track = no_track_fits` for **15 of 36** labelled postings, 42% [0.27, 0.58]. That
number and the 11.3% above are **different quantities on different instruments** and neither
bounds the other:

- 42% is a **prevalence** — how often *humans* said the posting fits no track, over 36
  postings.
- 11.3% is an **instability** — how often *the model* changed its mind about that boundary
  between two runs on the same text, over 115 postings.

A model that answered `null` for every posting would score 100% prevalence and 0%
instability. **This artifact cannot report the model's `null` prevalence at all**: the
selfcheck JSON stores aggregate cells and flip patterns, not per-record values, so the
denominator for a prevalence is not in the file. Anyone wanting that must compute it from an
`evals run --out` JSONL, which is a different artifact.

## The other sixteen fields do NOT supersede the committed run

This is the most important caveat in this document and it is easy to get wrong.

The committed `selfcheck-n120-2026-07-28.json` and this file are the same corpus, the same
model, the same n and the same three metrics — **but not the same prompt**, so the sixteen
shared fields are not a re-measurement of the same quantity.

The evidence is in the history, not in judgement:

- The committed artifact landed in `5092568` at **2026-07-28 03:57 -0400**.
- `role_track` entered `backend/extract.py` in `da4942c` (task 11) at **2026-07-28 13:57
  -0400** — ten hours *later* — and `303f7b9` changed `extract.py` again at **17:38**.
- `git diff 5092568..HEAD -- backend/extract.py` is 975 changed lines. It adds the
  `role_track` vocabulary and its instruction, and it substantially rewrites the
  `role_archetype` description with a new disambiguation paragraph.

So the 2026-07-28 prompt did not ask for `role_track`, and the field descriptions its answers
were drawn under are not the ones in force today. **Two different instruments.** A field that
reads differently between the two files is not evidence the model changed.

**Holding the corpus fixed was still the right call, and it is worth being exact about what it
bought.** It removes the *population* as an explanation, which is what choosing `corpus-v2`
over `corpus-v1` was for. It does not make the sixteen shared fields a same-instrument
re-measurement, because the prompt moved underneath them — the corpus was the confound that
could be eliminated, and the prompt is the one that could not. Movement on those fields is
attributable to the prompt, the model, or run-to-run noise, and **this run cannot separate
those three.** Anyone wanting a clean model-over-time reading needs the current prompt run
twice, which is not what this is.

**`role_track` has no prior figure to move from.** It is a first measurement, not a
re-measurement, and nothing here is a trend. There is no earlier `role_track` number in this
repo to compare it against, and a reader who finds one should suspect it is the human
`no_track_fits` prevalence rather than a model self-consistency figure.

Concretely: `ai_involvement` reads `agree2` **90.4%** [83.7–94.6] here. The committed figure
is `agree2` 94.8% [89.1–97.6]. The intervals overlap heavily, so the two are not even
distinguishable as measurements — but the prompt differs regardless, so the comparison is not
one that should be drawn at all. **[`../tasks/refactor/AUDIT.md`](../tasks/refactor/AUDIT.md)
§ *The three self-consistency metrics* remains the owner of the `ai_involvement` and
`seniority_level` figures under `DOCS-POLICY.md` rule 2, and this run does not replace
them.** What this run owns is `role_track`.

## Method

- **Instrument:** `backend/evals/` — `metrics.selfcheck()` and `metrics.field_cell()`.
- **Model:** `deepseek-v4-flash`, the production model, resolved from `backend/.env` through
  the repo's own `lib/envfile` loading (`evals/__main__.py:41`). Temperature 0
  (`llm.py:75`), timeout 120s.
- **Corpus:** `backend/evals/fixtures/corpus-v2.jsonl`, frozen. Which of the two frozen
  fixtures this is was a deliberate choice — see the next section.
- **n:** 120 records, of which 5 have no `description_text` and are skipped before any call is
  placed, because `extract.select_unextracted_jobs()` would never have sent them
  (`extract.py:180`). **115 usable in every repeat.**
- **Caching:** **off.** `--repeat > 1` disables it by default (`runner.run_repeated`) because a
  replayed answer has no variance in it. The log line confirms `cache=off`.
- **Passes:** 3, sequential, 3 workers each — matching `EXTRACT_MAX_WORKERS`, because latency
  measured at a concurrency the pipeline never uses is not the pipeline's latency.
- **Health:** 115/115 usable on every pass. **No tombstones, no deferrals, `not_ok` empty.**
  This is disagreement about content, not a flaky endpoint.

Nothing was tuned. No weights, no prompts, no vocabulary were touched in producing this.

## The corpus is v2, and that was a decision

The task as assigned named `corpus-v1.jsonl`. **This run used `corpus-v2.jsonl`**, and the
reason is recorded here rather than left to be rediscovered:

- `backend/evals/README.md:248-249` assigns them: `corpus-v1.jsonl` carries *"task 04's quota
  and wall-clock figures"*; `corpus-v2.jsonl` carries *"task 06's n=115 self-consistency
  figures"*.
- The committed run's own reproduce command ([`README.md`](README.md), § *The finding that
  should shape task 03*) reads `--corpus evals/fixtures/corpus-v2.jsonl`.
- The platform counts confirm it independently. The committed artifact's `platform_counts` is
  `builtin` 15 / `greenhouse` 17 / `hn_whoishiring` 21. `corpus-v2` yields exactly that (its
  20 `builtin` rows include the 5 with no description); `corpus-v1` would yield `builtin` 21 /
  `greenhouse` 18 / `hn_whoishiring` 19 and cannot produce the committed counts.
- `../labelling-report-2026-08-02.md` caveat 1 calls the thing this replaces *"the frozen
  n=115 fixture"*, singular.

Both are frozen fixtures, so both satisfy `../MEASUREMENT-TRAPS.md`'s rule against selecting a
corpus with `ORDER BY first_seen DESC`. The difference is comparability: measuring the
replacement on a different 115 postings would have confounded corpus with prompt, and the
prompt already moved (see above). This run holds the corpus fixed so that the one thing that
differs from 2026-07-28 is the prompt.
